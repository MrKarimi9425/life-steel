# راهنمای عمومی توسعه صفحات پنل مدیریت

## وضعیت سند

- نسخه: 0.1
- دامنه فعلی: ساختار صفحات فهرست، جدول، فیلتر، فرم و مودال
- مخاطب: توسعه دهندگان پنل مدیریت مبتنی بر React و TypeScript
- هدف: یکسان ماندن تجربه کاربری و ساختار کد در تمام پروژه ها

این سند وابسته به نام، داده یا نیازهای یک پروژه خاص نیست. پیش از ساخت یا بازنویسی هر صفحه پنل مدیریت باید این سند خوانده شود. بخش های مربوط به معماری بک اند، دیتابیس، احراز هویت، چند زبانه، تست جامع و استقرار در نسخه های بعدی به سند اضافه میشوند.

## واژه های الزام

- **الزامی**: باید در تمام پیاده سازی ها رعایت شود.
- **ممنوع**: نباید انجام شود، مگر پس از ثبت و تایید یک استثنا.
- **مجاز**: با توجه به نیاز صفحه قابل استفاده است.

## اصول پایه

1. صفحه باید هماهنگ کننده باشد، نه محل پیاده سازی تمام جزئیات.
2. هر بخش معنادار رابط کاربری باید کامپوننت مستقل داشته باشد.
3. منطق دریافت داده، وضعیت صفحه و نمایش رابط کاربری باید از هم جدا باشند.
4. پیش از ساخت کامپوننت جدید، کامپوننت های مشترک موجود باید بررسی شوند.
5. الگوی موجود پنل باید حفظ شود و توسعه موردی یا سلیقه ای ممنوع است.
6. یک قابلیت مستقل با چرخه ذخیره مستقل باید فرم یا مودال مستقل داشته باشد.
7. نسخه موبایل بخشی از تعریف کامل قابلیت است و بررسی آن اختیاری نیست.
8. حالت بارگذاری، خطا، داده خالی و عملیات در حال انجام باید از ابتدا طراحی شوند.

## ساختار استاندارد یک قابلیت

ساختار زیر قرارداد پایه است. اگر پروژه قابلیت ها را زیر یک دامنه گروه بندی میکند، همین ساختار داخل پوشه دامنه قرار میگیرد.

```text
features/
└── <feature>/
    ├── components/
    │   ├── <Entity>Filters.tsx
    │   ├── <Entity>Table.tsx
    │   ├── <Entity>FormDialog.tsx
    │   └── <Entity><Subresource>Dialog.tsx
    ├── hooks/
    │   └── use<Entity>Page.ts
    ├── api/
    │   └── <entity>.api.ts
    ├── types/
    │   └── <entity>.types.ts
    └── pages/
        └── <Entity>Page.tsx
```

اگر ساختار فعلی پروژه فایل های `api`، `types` و `hook` را مستقیما در پوشه قابلیت نگه میدارد، جابجایی آنها بدون تصمیم معماری جداگانه مجاز نیست. جداسازی مسئولیت ها الزامی است، اما تغییر ساختار موجود باید برای تمام قابلیت ها تصمیم گیری و اجرا شود.

## مسئولیت فایل ها

### فایل Page

فایل `<Entity>Page.tsx` فقط مسئول هماهنگی اجزای صفحه است:

- استفاده از hook صفحه
- اتصال فیلتر، جدول و مودال ها
- تعیین مودال فعال و موجودیت انتخاب شده
- ارسال callbackها و داده های لازم به کامپوننت ها
- چیدمان سطح بالای صفحه

موارد زیر نباید داخل فایل Page پیاده سازی شوند:

- تعریف کامل ستون های جدول
- JSX کامل فرم ایجاد یا ویرایش
- JSX مودال های جانبی
- فراخوانی مستقیم و پراکنده API
- تبدیل های پیچیده داده
- اعتبارسنجی فرم
- پیام های خطای موردی و متفاوت با الگوی پنل

نمونه ساختار:

```tsx
export default function EntityPage() {
    const page = useEntityPage()

    return (
        <>
            <ListPageLayout
                title="عنوان صفحه"
                subtitle="توضیح کوتاه صفحه"
                actions={<CreateEntityButton onClick={page.openCreate} />}
                filters={<EntityFilters {...page.filterProps} />}
            >
                <EntityTable {...page.tableProps} />
            </ListPageLayout>

            <EntityFormDialog {...page.formDialogProps} />
            <EntityDetailsDialog {...page.detailsDialogProps} />
        </>
    )
}
```

### hook صفحه

`use<Entity>Page` منبع اصلی وضعیت و رفتار صفحه است:

- پارامترهای جستجو و فیلتر
- صفحه فعلی و تعداد رکورد در صفحه
- موجودیت انتخاب شده
- نوع مودال فعال
- queryهای مورد نیاز صفحه
- mutationهای عمومی صفحه
- بازنشانی صفحه پس از تغییر فیلتر
- invalidation یا refresh داده پس از ذخیره موفق

hook نباید JSX تولید کند. خروجی hook باید به شکل propsهای آماده مصرف برای اجزای صفحه باشد تا اتصال اجزا در Page کوتاه و قابل فهم بماند.

### فایل API

فایل API فقط مرز ارتباط با سرور است:

- تعریف درخواست ها
- تعریف query keyها در صورت نیاز
- ارسال payload معتبر
- بازگرداندن نوع داده مشخص
- نرمال سازی محدود پاسخ، فقط زمانی که قرارداد سرور با نیاز کلاینت تفاوت دارد

نمایش toast، باز و بسته کردن مودال یا مدیریت state رابط کاربری در فایل API ممنوع است.

### فایل types

نوع های زیر باید در فایل type قابلیت قرار بگیرند:

- آیتم فهرست
- جزئیات موجودیت
- payload ایجاد و ویرایش
- پارامترهای فیلتر
- نوع مودال یا اکشن فعال
- props مشترک بین چند کامپوننت قابلیت

تعریف دوباره یک type یکسان در چند فایل ممنوع است.

## قرارداد صفحه فهرست

هر صفحه فهرست باید از چیدمان مشترک پنل استفاده کند و ترتیب آن ثابت باشد:

1. عنوان و توضیح صفحه
2. اکشن اصلی صفحه
3. جستجو و فیلترها
4. محتوای فهرست یا جدول
5. صفحه بندی
6. مودال های مستقل خارج از بدنه جدول

### عنوان و اکشن اصلی

- عنوان باید نام واضح موجودیت باشد.
- توضیح باید هدف صفحه را در یک جمله کوتاه بیان کند.
- اکشن اصلی مانند «ایجاد مورد جدید» باید در محل ثابت الگوی پنل قرار گیرد.
- اکشن های مربوط به یک رکورد نباید کنار اکشن اصلی صفحه قرار گیرند.

### اسکرول صفحه

- در دسکتاپ، ناحیه جدول میتواند اسکرول داخلی داشته باشد تا سربرگ و صفحه بندی در دسترس بمانند.
- در موبایل، عنوان، فیلترها، رکوردها و صفحه بندی باید همراه کل صفحه اسکرول شوند.
- ثابت ماندن بخش بالای صفحه و اسکرول شدن یک ناحیه کوچک جدول در موبایل ممنوع است.
- صفحه بندی در موبایل نباید به پایین viewport بچسبد و بخشی از رکورد را بپوشاند.

## فیلتر و جستجو

فیلترها باید در `<Entity>Filters.tsx` قرار گیرند و به صورت controlled کار کنند.

### الزامات

- مقدار هر فیلتر و callback تغییر آن از بیرون دریافت شود.
- تغییر فیلتر باید صفحه بندی را به صفحه اول برگرداند.
- گزینه «همه» برای فیلترهای اختیاری باید عنوان واضح داشته باشد.
- جستجو باید placeholder متناسب با داده قابل جستجو داشته باشد.
- فیلترها در موبایل باید تمام عرض و به ترتیب منطقی زیر هم قرار گیرند.
- پاک کردن فیلترها باید رفتار مشخص و یکسان داشته باشد.
- درخواست های جستجو باید در صورت نیاز debounce شوند.

### موارد ممنوع

- نگهداری یک نسخه از فیلتر در Page و نسخه دیگر در کامپوننت فیلتر
- ارسال درخواست جدید با هر کلید بدون debounce، زمانی که جستجو سمت سرور است
- استفاده از عنوان های مبهم مانند «انتخاب کنید» بدون ذکر نوع داده
- قرار دادن منطق دریافت گزینه ها داخل JSX فیلتر

## قرارداد جدول مشترک

تمام جدول های مدیریتی باید از کامپوننت مشترک جدول استفاده کنند. ساخت جدول خام برای یک صفحه فقط زمانی مجاز است که نیاز آن با قرارداد جدول مشترک قابل پوشش نباشد و استثنا پیش از پیاده سازی تایید شده باشد.

### مسئولیت `<Entity>Table`

- تعریف ستون ها
- تبدیل مقدارهای دامنه به نمایش قابل فهم
- نمایش badge یا status label
- تعریف اکشن های هر رکورد
- پاس دادن pagination و loading به جدول مشترک
- اعلام رویدادها به Page یا hook از طریق callback

این کامپوننت نباید خودش داده اصلی صفحه را دریافت یا mutation اجرا کند.

### ستون ها

- هر ستون باید `id` پایدار یا `accessorKey` مشخص داشته باشد.
- عنوان ستون باید کوتاه و قابل فهم باشد.
- داده خالی باید با یک نمایش استاندارد مانند `—` مشخص شود.
- وضعیت های enum باید به برچسب قابل فهم تبدیل شوند.
- تاریخ، عدد و متن باید با formatter مشترک نمایش داده شوند.
- ستون اکشن باید شناسه ثابت `actions` داشته باشد.
- عرض ثابت فقط برای ستون هایی تعریف شود که واقعا به آن نیاز دارند.

### اکشن های رکورد

- اکشن ها باید داخل کامپوننت مشترک `TableActions` قرار گیرند.
- هر اکشن باید icon، `aria-label` و tooltip واضح داشته باشد.
- رنگ اکشن باید معنای ثابت داشته باشد؛ برای نمونه حذف همیشه tone خطر دارد.
- کلیک روی اکشن نباید ناخواسته رویداد کلیک رکورد را اجرا کند.
- ترتیب اکشن ها در جدول های مشابه باید ثابت باشد.
- عملیات مخرب باید تایید مناسب داشته باشند.

### hover

- hover باید روی تمام سلول های رکورد اعمال شود.
- تغییر رنگ فقط یک سلول یا فقط بخش اکشن در hover مجاز نیست.
- رنگ hover باید در حالت روشن و تاریک قابل تشخیص باشد.

### حالت موبایل جدول

در عرض موبایل، اسکرول افقی جدول انتخاب پیش فرض نیست. جدول مشترک باید هر رکورد را به کارت تبدیل کند:

- هر رکورد یک کارت مستقل است.
- عنوان ستون کنار مقدار همان ستون نمایش داده میشود.
- متن ها میتوانند چند خطی شوند و نباید به `nowrap` محدود بمانند.
- اکشن ها در پایین کارت و در یک بخش قابل تشخیص نمایش داده میشوند.
- اکشن ها در صورت کمبود عرض wrap میشوند.
- ستون اکشن در موبایل sticky نیست.
- ترتیب اطلاعات کارت مطابق ترتیب ستون های نسخه دسکتاپ است.
- حالت تاریک، border و hover کارت باید با design system هماهنگ باشند.

اسکرول افقی فقط برای داده هایی مانند ماتریس، گزارش عریض یا مقایسه چند ستونه مجاز است که تبدیل آنها به کارت باعث از دست رفتن معنا میشود. این استثنا باید آگاهانه و برای همان جدول ثبت شود.

### صفحه بندی

- جدول باید از صفحه بندی مشترک استفاده کند.
- تعداد رکوردهای هر صفحه باید از گزینه های استاندارد پنل انتخاب شود.
- تغییر تعداد رکورد باید صفحه فعلی را به مقدار معتبر برگرداند.
- در موبایل فقط کنترل های ضروری صفحه بندی نمایش داده شوند.
- صفحه بندی باید بعد از آخرین رکورد قرار گیرد و بخشی از کارت را نپوشاند.

### حالت بارگذاری

- هنگام دریافت داده باید skeleton متناسب با جدول یا کارت نمایش داده شود.
- ارتفاع skeleton نباید باعث پرش شدید چیدمان شود.
- کنترل مرتب سازی و اکشن های وابسته هنگام بارگذاری باید غیرفعال باشند.
- جایگزین کردن کل صفحه با spinner در صفحات فهرست مجاز نیست، مگر در بارگذاری اولیه ساختار اصلی برنامه.

### حالت داده خالی

حالت خالی باید شامل موارد زیر باشد:

- icon مشترک
- پیام واضح
- در صورت مناسب بودن، اکشن ایجاد اولین رکورد

پیام حالت خالی باید بین «هنوز داده ای ایجاد نشده» و «نتیجه ای برای فیلتر پیدا نشد» تفاوت قائل شود.

### حالت خطا

- خطای دریافت جدول باید داخل محدوده محتوا نمایش داده شود.
- در صورت قابل تکرار بودن درخواست، اکشن تلاش مجدد ارائه شود.
- نمایش همزمان جدول قدیمی و خطای مبهم بدون مشخص کردن وضعیت داده ممنوع است.
- پیام خطا باید با سیستم استاندارد خطا و toast پنل هماهنگ باشد.

## فرم ایجاد و ویرایش

فرم اصلی باید فقط اطلاعات اصلی موجودیت را مدیریت کند. معیار اصلی، وابستگی و چرخه ذخیره است، نه تعداد ظاهری فیلدها.

### موارد مناسب برای فرم اصلی

- اطلاعات هویتی موجودیت
- وضعیت انتشار یا فعال بودن
- داده های اصلی چند زبانه
- ارتباط های اصلی و ضروری

### موارد مناسب برای مودال مستقل

- گالری و رسانه
- ویژگی ها و مشخصات قابل تکرار
- ارتباط های چندتایی مانند موارد مرتبط
- تاریخچه یا یادداشت ها
- زیرمنبعی که API و ذخیره مستقل دارد
- بخشی که باعث طولانی و مبهم شدن فرم اصلی میشود

### قرارداد `<Entity>FormDialog`

فرم باید حداقل این ورودی ها را داشته باشد:

```ts
type EntityFormDialogProps = {
    open: boolean
    entityId: string | null
    onClose: () => void
    onSaved: () => void
}
```

در صورت نیاز، optionها و dependencyهای آماده نیز از بیرون دریافت میشوند.

### رفتار فرم

- حالت ایجاد و ویرایش باید از `entityId` مشخص شود.
- با هر بار باز شدن، state فرم باید از منبع معتبر مقداردهی شود.
- بعد از بسته شدن، خطا و state موقت فرم نباید به باز شدن بعدی نشت کند.
- دکمه ذخیره هنگام mutation غیرفعال و دارای وضعیت loading باشد.
- خطای فیلد کنار همان فیلد نمایش داده شود.
- خطای عمومی با toast استاندارد نمایش داده شود.
- بعد از ذخیره موفق، داده فهرست refresh و مودال طبق قرارداد بسته شود.
- footer مودال باید فاصله ایمن از پایین داشته باشد و آخرین فیلد به لبه پایین نچسبد.

## مودال های جانبی

هر مودال جانبی باید فایل مستقل داشته باشد. ساخت مودال کامل داخل Page یا Table ممنوع است.

نام گذاری:

```text
<Entity>MediaDialog.tsx
<Entity>AttributesDialog.tsx
<Entity>RelationsDialog.tsx
```

### الزامات

- مودال فقط هنگام باز بودن داده مورد نیاز را دریافت کند.
- mutation مودال فقط بخش مربوط به خودش را ذخیره کند.
- ذخیره یک زیرمنبع نباید payload کامل و نامرتبط موجودیت را ارسال کند.
- مودال باید loading، empty، error و saving مستقل داشته باشد.
- عنوان مودال باید نام عملیات و موجودیت انتخاب شده را روشن کند.
- بسته شدن مودال نباید فیلتر یا صفحه فعلی فهرست را از بین ببرد.

## کامپوننت مشترک یا اختصاصی

### کامپوننت مشترک بسازید وقتی

- یک الگوی رفتاری در چند قابلیت تکرار میشود.
- قرارداد ورودی و خروجی آن بدون وابستگی به دامنه قابل تعریف است.
- تفاوت ها با props محدود و قابل فهم پوشش داده میشوند.
- یک design system یا رفتار ثابت پنل را اجرا میکند.

نمونه ها:

- `ListPageLayout`
- `DataTable`
- `TableActions`
- `TableActionButton`
- `FormDialog`
- `RelationMultiSelect`
- `MediaPicker`
- empty state و error state

### کامپوننت اختصاصی قابلیت بسازید وقتی

- نمایش به typeهای دامنه وابسته است.
- ستون ها یا فیلدها معنای تجاری مشخص دارند.
- رفتار فقط در همان قابلیت معتبر است.

کامپوننت مشترک نباید با تعداد زیادی prop شرطی به یک کامپوننت همه کاره تبدیل شود. در مقابل، کپی کردن یک الگوی موجود و تغییر جزئی آن نیز ممنوع است.

## نام گذاری

- نام موجودیت در کامپوننت ها به صورت PascalCase نوشته شود.
- hook با `use` شروع شود.
- فایل API با نام موجودیت و پسوند `.api.ts` نوشته شود.
- typeهای list، detail و payload نام متفاوت و صریح داشته باشند.
- callbackها با `on` و handlerهای داخلی با `handle` شروع شوند.
- booleanها با `is`، `has`، `can` یا `should` شروع شوند.
- شناسه رکورد انتخاب شده به صورت `<entity>Id` نگهداری شود، نه یک نام عمومی مانند `selected`.

## الگوی وضعیت مودال ها

برای صفحه ای با چند مودال، یک state صریح بهتر از چند boolean مستقل است:

```ts
type EntityDialogKind = 'form' | 'media' | 'relations' | null

type EntityDialogState = {
    kind: EntityDialogKind
    entityId: string | null
}
```

این الگو از باز شدن همزمان چند مودال و stateهای ناسازگار جلوگیری میکند.

## موارد ممنوع

- تعریف فیلتر، جدول، فرم و چند مودال بزرگ در یک فایل Page

- نگهداری چند منبع state برای یک مقدار
- ارسال payload کامل برای ویرایش یک زیرمنبع مستقل
- استفاده از index آرایه به عنوان شناسه پایدار رکورد

- نمایش خطا با روش متفاوت در هر صفحه
- قرار دادن متن بدون label برای اکشن های icon-only

3. فایل API و query keyها را تعریف کنید.
